# Baseline congelado `BASELINE-2026-08-03`

O Método §6.2 exige que o baseline seja versionado **antes** da otimização, e que qualquer
mudança posterior force novo comparativo. Este documento é o congelamento.

> Alterar qualquer item abaixo invalida toda comparação feita contra ele. Não edite: crie
> `BASELINE-<nova-data>` e registre a transição no `DECISION_LOG`.

Picos são publicados; **tudo abaixo da linha de capacidade é premissa não medida** (`G-003`).

## Workload de referência

| Parâmetro | Valor |
|---|---|
| prompt | 2048 tokens |
| geração | 512 tokens |
| lote | 1 |
| contexto em decode | 2304 (prompt + metade da geração) |
| precisão de pesos | bf16 (nativa do modelo) |
| precisão de ativação | bf16 |

Escolha do lote 1: é o pior caso econômico e o mais citado em demonstrações de latência. A
[TRANSFORMATION_MATRIX](../../03_UNIFICATION/TRANSFORMATION_MATRIX.md) mede o efeito de sair dele.

## Modelo de referência

`llama-3.1-8b` — 8.030.261.248 parâmetros derivados da IR, idêntico ao valor publicado.

## Como reproduzir

```bash
PYTHONPATH=src python -m silicon_atlas.cli profile llama-3.1-8b \
  --device h100-sxm --batch 1 --prompt 2048 --gen 512
```

Determinístico: nenhuma aleatoriedade no caminho do profiler.

## Condições de invalidação

Este baseline deixa de valer se qualquer uma ocorrer:

1. `config/devices.json` mudar para `h100-sxm` — inclusive eficiências assumidas;
2. `corpus/models/llama-3.1-8b.json` mudar;
3. o modelo de custo em `profiler.py` ou `ir/graph.py` mudar de forma a alterar FLOPs ou bytes;
4. `G-003` fechar — a calibração contra latência medida **substitui** este baseline, não o ajusta.

O item 3 já ocorreu uma vez durante o ciclo: a correção do gather de embeddings mudou o tráfego
de decode. Os números acima são pós-correção. Registrado no
[CHANGELOG](../../07_SYSTEMATIZATION/CHANGELOG.md).
